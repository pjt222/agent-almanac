## Run: 2026-08-25-fence-strip-replication

**Observer**: Claude (Opus 5, one Claude Code session on one machine) | **Issue**: #721 | **Relates**: #407, #717, #722, `anthropics/claude-code#82056`

### Objective

The `fenced` arm of the [2026-08-23 run](../2026-08-23-memory-cap-truncation-probe/RESULT.md) is the
**only cell in that corpus that resists a width-only reconstruction** — it returned 109 where the
geometry predicts 124 — which makes it the single most load-bearing measurement in the set, and the
one the shipped fence-state repair in `skills/manage-memory` rests on.

It had been exercised with exactly one fence tag: ```` ```text ````. That document says so in its
Boundaries section. #721 is the replication it asks for, and it turns on one case in particular:
**an untagged fence**, which is what this repository's own default-deny i18n fence rule
(CLAUDE.md § Which code fences are frozen) treats as frozen on arrival. If untagged fences behaved
differently under the memory-index strip, that rule's rationale and this measurement would disagree.

### Method, and a deliberate deviation from the issue's spec

#721 prescribes a **behavioural** protocol: invented-token needles right-aligned at lines 108/109/110
and 123/124/125, three trials each, classified on presence of the exact planted value, with a
disk-only decoy asserting tool-zero.

**This run does not use it.** That entire apparatus exists to defend a read-out that goes through the
model — an absent needle returns no `UNKNOWN` token in two of three observed modes, fabricates a
plausible value in roughly 2% of trials, and a tool-stub failure can score a *present* needle as
absent. #722 established a strictly better instrument: [`tools/wirecap.py`](../../../tools/wirecap.py)
captures the request body the client actually sends, so the loaded prefix is **read** rather than
inferred. Every hazard in that list is a property of asking the model, and none survives the change.
Three trials collapse to one observation, and the classifier collapses to "which lines are in the
bytes".

It is also **more** informative, which is the part that matters. The needles can only see where the
canaries stop, so `stripped` and `counted` are the only hypotheses they can express. Reading the wire
shows the comment's presence and the cut *independently*, separating four cases where the needles see
two:

| comment in context | cut | reading |
|---|---|---|
| absent | 124 | stripped, and not counted — the documented behaviour |
| present | 109 | preserved, and counted |
| absent | 109 | stripped from the text but still charged to the budget |
| present | 124 | preserved but not charged |

The #721 acceptance criteria ask which verdict each tag returns, not that the needles produce it, so
they are met — by a method that cannot return the failure modes they were written to absorb.

**"Strictly better" was too strong, and one control was dropped without saying so.** The three
trials did a second job: the 2026-08-23 run says "two runs per cell agreed everywhere, which bounds
flakiness". This run is **n = 1 per arm** and bounds nothing. Cross-arm replication substitutes for
claims 3–5, where five fenced arms agree, but claims 1 and 2 each rest on a single observation of a
single arm. The instrument is better against every hazard the needles were defending against; it is
not better in every respect, and run-to-run stability is the respect it is worse in.

### Fixtures

Eight arms, generated by [`fence-strip-probe.py`](fence-strip-probe.py), differing only in what
precedes an identical body of 150 canary lines at 201 units each.

| arm | lines | units | block units | `stripped` predicts | `counted` predicts |
|---|---:|---:|---:|---:|---:|
| `ctrl` | 150 | 30,149 | 0 | 124 | 124 |
| `bare` | 167 | 33,173 | 3,024 | 124 | 109 |
| `midbare` | 167 | 33,173 | 3,024 | 124 | 109 |
| `text` | 169 | 33,185 | 3,036 | 124 | 109 |
| `yaml` | 169 | 33,185 | 3,036 | 124 | 109 |
| `bash` | 169 | 33,185 | 3,036 | 124 | 109 |
| `json` | 169 | 33,185 | 3,036 | 124 | 109 |
| `untagged` | 169 | 33,181 | 3,032 | 124 | 109 |

`block units` counts the comment, any fence delimiters, **and** the newline separating the block from
canary 1 — which is why `bare` is 3,024 and not 3,023, and why these figures match #721's published
spec. The distinction changes no verdict here (`floor((25000-3023)/201)` and
`floor((25000-3024)/201)` are both 109), which is exactly why an off-by-one would have gone unnoticed.

**Maximum 169 lines, against a 200-line cap.** No arm can reach the line cap even with the block
counted, so the size cap is the only thing that can move the cut. A 200-line fixture would let the
line cap fire in the counted case and produce the right answer by the wrong mechanism.

#### No tested info string changes the answer

All five fenced arms — four distinct info strings and **no info string at all** — return the same
verdict, with all 15 comment lines present in context. `untagged` is indistinguishable from `text`.

This is the case #721 was filed for, and it is the case the repository's default-deny fence rule
turns on. **The rule's rationale and this measurement agree**: an untagged fence is a fence. Nothing
in CLAUDE.md § Which code fences are frozen needs revisiting, and the shipped detector in
`skills/manage-memory` — which toggles fence state on any line whose first non-space characters are
```` ``` ````, with no tag inspection — is now measured correct for all five variants rather than
inferred from one.

#### The fence is the variable, not the position — measured, after a review found the confound

The first seven arms could not establish what they claimed. In every one of them the bare comment
sits at the **file start** while every fenced comment sits at **line 2**, after the fence opener.
So a frontmatter-like rule — *strip a block comment only at the top of the file* — predicts all
seven observations exactly as well as "the fence prevents the strip". The 2026-08-23 run has the
same shape, so nothing in the corpus discriminated them, and the causal claim was resting on the
arm design rather than on evidence.

`midbare` is that control: byte-count-identical to `bare` (167 lines, 33,173 units, block 3,024),
differing only in that **one canary precedes the comment**.

```
bare      <!-- … -->  CANARY-001 … CANARY-150      cut 124, 0 comment lines, notice 29.4KB
midbare   CANARY-001  <!-- … -->  CANARY-002 …     cut 124, 0 comment lines, notice 29.4KB
```

A position rule predicts `midbare` at **109 with 15 comment lines present**. It measured **124
with none**. **The position hypothesis is refuted**: a bare block comment is stripped wherever it
sits, and the fence is the operative variable.

This also settles a live worry about the shipped code. `skills/manage-memory`'s detector strips
bare comments at *any* position outside a fence, and its Step 6 tells users a mid-file curator
comment is invisible to the budget. Had position been the rule, the detector would have been
stripping content the harness counts — under-reporting usage, the direction this corpus calls
dangerous. It is not; both are correct.

#### A second, independent read-out in the same capture

The truncation notice discovered in #722 states the file's size, and it corroborates the verdict from
a completely different signal:

- `ctrl` (30,149 units) and `bare` report **29.4KB**. `bare`'s raw file is 33,173 units = 32.4KB, so
  its notice is reporting the **post-strip** size, exactly `ctrl`'s display figure. So the strip
  happens **before** the size is measured. Note what that does *not* pin: `33,173 − 3,024 = 30,149`
  is arithmetic, and at 0.1KB ≈ 102-unit resolution the notice cannot separate 30,149 from 30,150 —
  so whether the separator newline goes with the block is below the instrument's resolution and
  moves no verdict. (`bare`'s raw 33,173 units is 32.3955, the one figure here sitting where
  round-half and truncate disagree; nothing pins that mode, and 29.4 is neither, so no conclusion
  depends on it.)
- All five fenced arms report **32.4KB**, their full file size. Nothing was stripped.

The resolution is ample for the job — stripped and preserved are 3.0KB apart, roughly 30× the
display resolution — and **useless for separating untagged from tagged**, which differ by 4 units.
It corroborates claims 2, 3, 6 and 7; it adds nothing to claims 4 and 5, and the table above does
not use it for those.

Both read-outs are now recorded by the probe itself. The first version stored only a boolean and
the KB column was hand-read off an uncommitted capture, so the published table could not be
regenerated by the published commands — `results.json` now carries `notice_kb`, `notice_limit_kb`
and `contiguous`, and a non-contiguous capture annotates its own verdict instead of printing a
clean one.

### What this changes elsewhere

- The 2026-08-23 Boundaries line "```text is the only fence tag exercised" is **retired**, and is
  annotated in place.
- That document's boundary "the instrument is the model's own report of what it can see, **not a
  captured wire trace**" is likewise retired — one now exists, and its `fenced` cell agrees with the
  behavioural one.
- **The `fenced` cell's standing under the #717 reconstruction ruler is unchanged, and is now
  stronger.** It was the one cell not reachable by width-only arithmetic; it is now that cell
  replicated on a second build, by an instrument the ruler does not apply to, five times over. The
  #722 finding that the harness states the cap in the prompt does not rescue it either: knowing the
  cap and the width still does not tell you whether the comment is charged.
- `skills/manage-memory` needs **no change**. Its detector already ignores the info string, and this
  run measures that as correct rather than assuming it.

### What this run does NOT claim

- **One build, one platform.** 2.1.245, linux-x64, WSL2, one machine. Note that the 2026-08-23
  arms ran on 2.1.241, so where the two instruments agree they confirm instrument soundness AND
  no-build-change **jointly** — a disagreement could not have been attributed to either.
- **One observation per arm.** No run-to-run stability bound, unlike the predecessor's two runs
  per cell. Five agreeing fenced arms carry claims 3–5; claims 1 and 2 are single observations.
- **Five info strings, not all of them, and tag LENGTH is invisible here by construction.** The
  four tagged arms are all 4-letter tags and therefore geometrically identical at 3,036 units —
  but that costs nothing, because `counted = 109` holds for any block in (2,890, 3,091], so a
  2-letter or 10-letter tag predicts the same observables, and `untagged` already spans the length
  axis. The untested axis is adversarial tag **content**: ```` ```html ````, the language of the
  comment itself and the single most plausible special case, and ```` ```md ````/```` ```markdown ````,
  the tags this repo's own fence rule exempts.
- Nothing here tests a tag with attributes (```` ```js {highlight} ````), an indented fence, a
  `~~~` fence, or a fence that is never closed — the last being the interesting one, since the
  shipped detector toggles rather than tracking nesting.
- **Nothing about YAML frontmatter**, which the documentation groups with HTML comments and which no
  arm here exercises.
- **Nothing about whether the model attends to any of this.** The read-out is what was sent.
