## Run: plugin workflow loader probe (issue #293, Q1 and Q2)

**Date**: 2026-11-24 | **Binary**: Claude Code **2.1.331** (`claude --version`) | **Model**: `--model sonnet` | **Repo HEAD at run**: `1a29fcc5b6e786c9cc242a9808bb4f4291745a0d` (read by hand after the runs from the checkout the plugin copies were archived from; that checkout's HEAD reflog shows it at this sha from before the runs until the read; the script did not capture it, and the `.commit.sh` versions now do)

### Question

A static read of the 2.1.330 binary (the motivation for this probe; that read is not re-derived here) says the plugin loader reads a plugin's workflows path, keeps only `.js` files, and registers each as `<plugin>:<meta.name>`. Two things were unmeasured:

- **Q1**: does a plugin's `.js` workflow register as `<plugin>:<meta.name>` in a live session?
- **Q2**: does this repository's plugin (`.claude-plugin/plugin.json` with no `workflows` field; `workflows/*.mjs`) load none of its workflows?

### Where the manifest key comes from

Every static claim below was read from the installed **2.1.331** binary (`strings -n 8`; the dump carries `VERSION:"2.1.331"` (171 lines) and no other Claude Code version stamp; its one `2.1.330` string is an embedded changelog heading, and its one other `VERSION:"<x.y.z>"` match is a semver library's `SEMVER_SPEC_VERSION`), not from the docs. It is a static read of minified code, and no minified name is quoted here.

- **Default directory**: the loader sets the plugin's `workflowsPath` to `<plugin root>/workflows` only when three conditions hold. (1) The manifest has no `workflows` field. (2) The folder is present. (3) The folder was not refused by the loader's path-traversal check. Condition 2 is the workflows entry of the loader's per-folder presence results: an existence check on `<plugin root>/workflows` (a minified filesystem call that was not traced further) or, for a cache-installed plugin, a plugin-cache listing. The same pattern covers the commands, agents, output-styles and themes folders; the skills folder has no manifest-field condition.
- **Manifest field**: `workflows` (a string or an array; each entry a directory, or a single `.js` file with its own `custom file` load line), resolved into a separate path list by a statement that follows the default-directory one. It is not an else branch of it.
- **Replace or add, read statically**: because condition 1 names the field, setting it switches the default directory off. The binary also carries a plugin diagnostic for this case, a template `Default <component>/ folder is ignored because the manifest sets <fields>`; for workflows the field list is the single entry `workflows` or `experimental.workflows`. The list formatter was not read, so the exact rendered string is a reconstruction. Its remedy text, when exactly one field is listed, says to remove the field from the manifest to auto-load the folder, "or add the folder's files to the <field> list if you want both" (with several fields only the remove advice is given). That remedy is advice; it does not describe the loader's mechanism and does not establish that listing files is the only way to keep the folder. The diagnostic is raised only inside a block that requires the manifest `workflows` field to be set and the folder to be present (condition 2's flag), and inside it only when a coverage helper returns false. The helper takes the entries (a string, an array of strings, or the `source` values of an object), resolves each against the plugin root, and returns true when any resolved path plus a separator starts with the folder path plus a separator. It is passed only the plain `workflows` field; the `experimental.workflows` name only selects the label in the message. What the capture does **not** show: any live run with the field set, and how an `experimental.workflows` spelling of the field is normalised before this point (not traced). This probe did **not** use the manifest field; it used the default directory, because that is the situation of this repository's plugin.
- **Filter and name**: the directory loader keeps entries whose name ends in `.js` and keys each by `` `${plugin.name}:${meta.name}` ``.
- **Load log lines in the binary**: `Loaded N workflows from plugin <name> default directory` / `... custom path: <path>`.

### Method

Design follows `tests/results/2026-10-14-workflow-loader-probe/probe.sh`: one fresh scratch project per arm (`git init`), one headless `claude -p` session per arm, `Workflow` tool_use / tool_result and the `init` event read from the stream-json log with `jq`, never from model prose. No `agent()` call in any authored probe workflow (each body is `log(<marker>)` plus a `return`); arm G adds a byte copy of a repository workflow whose body does call `agent()`, which was registered and never run. `CLAUDECODE`, `CLAUDE_CODE_*` (except OAuth, `USE_*` and API-key helpers), `CLAUDE_PID` and `CLAUDE_EFFORT` were removed with `env -u` (the rule is spelled out under Files). Settings were not isolated: the operator's user-installed plugins and three SessionStart hooks (each exit 0) were active in every arm, and none contributed a workflow (the `Available:` lists in B, D, E and G hold only `deep-research` besides the probe entries, and the 452/453 slash-count parity agrees; the `init` slash-command list itself is untyped and cannot by itself show which entries are workflows). The user-scope `~/.claude/workflows` directory did not exist (checked by hand after the runs, not captured at run time), and no `agent-almanac` plugin is installed, so neither can contaminate arm D or E.

Exact flags for every arm (the prompt differs only in the workflow name; `--plugin-dir` is absent from arm C):

```text
claude -p "Run the saved workflow named <NAME> using the Workflow tool: pass only the name parameter, no script and no scriptPath. If the tool returns an error, show it verbatim and stop. If it succeeds, wait for it to complete, report its exact return value verbatim, then stop." --output-format stream-json --verbose --model sonnet --effort low --permission-mode dontAsk --strict-mcp-config --max-budget-usd 0.50 --allowedTools Workflow [--plugin-dir <dir>]
```

Per-arm timeout 240 s. All seven children (five in run 1, two in run 2) exited 0 with empty stderr. Cost: B, D, E and G each reported one `result` event at about 0.115 USD; A, C and F each reported two (the first about 0.118, the last about 0.128 USD `total_cost_usd`). A, C and F each emitted a second `init` and `result` event after the task notification (B, D, E and G one each). Whether the figure is cumulative was not checked.

Scratch plugin `probeplug`: `.claude-plugin/plugin.json` with `name: probeplug`, no `workflows` field, and `workflows/probe-a.js` whose `meta.name` is `probe-a-name` (distinct from the stem). The repository copy was made with `git archive HEAD .claude-plugin workflows` (the skills and agents trees were left out; see Limits).

### What each verdict rests on

- **Q1 (plugin `.js` registers as `<plugin>:<meta.name>`)** rests on arm A, with arm C as the control that the harness can resolve and run a workflow at all, and arm B as the negative that the bare name is not an alias. The three agree: the registered name is namespaced, `meta.name` and not the file stem supplies the second half, and the Workflow tool's own `Available:` list in B names the entry. Arm A's call carried only `name`, so the lookup was the thing measured. The body ran: `task_updated` and `task_notification` report `completed` in the stream, and the runtime's own run record (`wf_<runId>.json` in the arm's session directory, see Files) carries the marker in `logs`. Each record's `taskId` equals the Task ID in its arm's `tool_result` (A `wip2osbo2`, C `we4xgt1zr`), so the record belongs to that arm's own call.
- **Which name supplies the prefix.** In arm A the plugin directory and the manifest name coincide (`probeplug`), so run 1 alone could not tell them apart. Run 2 can: in arms F and G the directory is `repoplugF` / `repoplugG` and the manifest name is `agent-almanac`, and the registered key is `agent-almanac:<meta.name>`. The prefix is the manifest name (measured, one run, inline `--plugin-dir` loading; a version-directory install was not run).
- **Q2 (this repository's plugin loads none of its workflows)** rests first on the D and E `init` slash commands containing no `agent-almanac:` entry at all, where A, F and G show a plugin workflow does appear there as `<plugin>:<meta.name>`; slash count 452 versus 453 agrees. The `Available:` list corroborates it: both the namespaced and the bare call failed with the lookup's own text, and the list holds only `deep-research`, which is also what the no-plugin projects of the 2026-10-14 probe reported (it is not a workflow of this repository). "Loads none of them" is read from D and E for `verify-handoff` only; for the other `.mjs` files it rests on the `init` slash commands and `Available:` list holding no `agent-almanac:*` entry.
- **Why the `.js` extension matters.** A and D differ in more than the extension (plugin name, manifest fields, directory name, number of entries, a `README.md`), so that pair is not a one-variable contrast. Arm F shows the default directory is scanned under the real manifest and that the `.mjs` files beside a `.js` register no entry. Arm G adds that a real repository workflow registers once it is a `.js` file, and that the three differently named `.mjs` files stay unlisted. Arm G cannot show that `verify-handoff.mjs` itself was skipped, because the `.js` copy and the original share one `meta.name` and the registry is keyed by name; the 2026-10-14 probe deliberately left that arm design out for the same reason. The `.mjs`-excluded reading therefore rests on F, on G's three other names, and on D and E, together with the static `.js` filter.

### Limits

- One binary (2.1.331), seven arms, each run once, one model. No arm was repeated.
- The motivating static read was of 2.1.330; every static claim above was read from the 2.1.331 dump only.
- Run 2 (arms F and G, same flags and environment scrub as run 1, script `run2.commit.sh`, both exited 0 with empty stderr) was added after review. In G the `.js` copy was registered but never executed, so that a repository workflow's body (which calls `agent()`) runs correctly as `.js` is not measured. Registration was read from `init` slash commands and the `Available:` list, neither of which needs the body to run.
- The three-condition default-directory guard was read statically (the folder-present flag's existence check is a minified call that was not traced). Run 2 shows the directory is scanned under this repository's real manifest (no `workflows` field), so the guard passes there.
- **Not measured live, for #293:** that setting a manifest `workflows` field disables the default directory. The static read predicts it does (condition 1 and the loader's own "default folder is ignored" diagnostic), so adding the field without covering the folder would drop the default `workflows/` directory. How to keep both is a static read only. For a directory loaded with `--plugin-dir`, the binary answers both the loading half and the diagnostic half (below); for an installed plugin or a zip, only the loading half. The diagnostic is raised only when the field is set, the `workflows/` folder is present, and the coverage helper (below) finds no entry whose resolved path is the folder path or lies under it. Entries resolve relative to the plugin root, and an entry that escapes the root is refused (the loader logs `path ... escapes plugin directory`). The manifest schema's own description of the field says the same: a path to a workflows directory or `.js` file, relative to the plugin root; when set, the `workflows/` directory is not auto-loaded, and "list its files here if you want both". The custom-path branch loads a directory entry through the same directory loader as the default folder, and loads a file entry only when its name ends in `.js`, with no other branch. So a `workflows/` directory entry should keep the folder, and for a directory loaded with `--plugin-dir` it should also silence the diagnostic. The coverage helper compares each entry, which it resolves to an absolute path, with the folder path `path.join(<plugin root>, 'workflows')`, which is absolute only if the plugin root is. For each entry that is not a URL, the inline loader resolves the flag's value with `path.resolve` and hands the result to the plugin loader as the root. The one branch that replaces that root before the call, for a synced plugin directory that has gone, resolves its successor the same way, and the plugin loader does not reassign the root before the check. Both sides of the comparison are therefore absolute and normalised. Any single file entry inside the folder silences the diagnostic too, so a silent diagnostic does not show that every file in the folder is listed, and a `.mjs` file entry would load nothing and still silence it. This is a static read of that chain, made by one reviewer and re-derived by the lead from the dump; the `.zip` branch and the root an installed plugin reaches the loader with were not traced, and the arms cannot test it either way, because every `--plugin-dir` value they passed was already absolute. None of this was run. That the path separator in the coverage helper is Node's `sep` is inferred from use (the import sits in the same module, under the same short name, which other modules of the dump rebind), and how an `experimental.workflows` spelling is normalised was not read. No arm set the field. A one-arm live probe (the real manifest plus a `workflows` field, with a `.js` in `workflows/`; variants: a file entry, a `.mjs` file entry, a `workflows/` directory entry, an entry pointing elsewhere) would settle it.
- `--plugin-dir` (inline) loading was measured. A marketplace-installed plugin goes through the same directory loader per the static read, but folder detection can go through a plugin-cache listing, the loader has a per-file check that applies only to plugins carrying an install anchor (an inline plugin may not exercise it), and a source-keyed filter runs after loading. None of these was resolved, and the install path was not run.
- Collision behaviour between two plugins, or between a plugin workflow and a project workflow of the same `meta.name`, was not tested.
- The repository copy omitted the skills and agents trees; that is not expected to affect workflow loading but was not tested.

### Files

Not for commit: the scratch `run1/` and `run2/` directories (`arm-*.stream.jsonl`, `cmdline.txt`, `stderr.txt`, `exitcode.txt`, the `extracted.json` files, `env-scrub.txt`, `version.txt`), whose raw logs hold home paths, session ids and the operator's installed-plugin list, and the 87 MB `strings` dump of the binary used for the static reads. For commit, with placeholders:

- `scripts/run.commit.sh` (arms A to E) and `scripts/run2.commit.sh` (arms F and G). The scripts that ran hardcoded the real scratch output path (project slug and session id included) in an outdir equality check, and the repository path; do **not** commit `run.sh` or `run2.sh`. The `.commit.sh` versions replace the equality check with a refusal to run inside a git repository and a refusal of a relative outdir, take the repository checkout as an argument, and add two capture lines that were not in the run (`git rev-parse HEAD` and a listing of the user-scope workflows directory). Otherwise they are identical to the scripts that ran, `diff`-checked.
- `scripts/extract.commit.sh`: reduces a stream log to the fields the tables read (calls, first line of each result, slash counts and workflow entries per `init`, inline plugin only, task events (a `task_updated` status is read from its `patch` object, a `task_notification` status from its top level), every `total_cost_usd`). The original `arm-*.extracted.json` were produced by a script that was not captured and carry the full installed-plugin list, so they are not committed; the outputs of this script replace them: `commit-extracts/arm-{A,B,C,D,E,F,G}.json`.
- `commit-extracts/arm-{A,C}.run-state.json`: reduced from the runtime's `wf_<runId>.json` under each arm's session directory in the Claude Code project store (`<home>/.claude/projects/<slug>/<session-id>/workflows/`), keeping `taskId`, `workflowName`, `status`, `logs`, `result` (projection: `jq '{taskId, workflowName, status, logs, result}' <wf_runId.json>`; re-run against the live records it reproduces both committed files byte-for-byte). That store is deleted after the retention period, so these copies are the durable evidence that the body ran.
